# TrustPay Integration

This example store shows how to integrate with TrustPay payments. The store owner has to create a TrustPay account using the exact username he will later provide as `storeName` in payment requests. The money that users pay at the store will be transferred directly to that account.

Flow:
1. The customer generates a 6-digit code in the TrustPay app (valid for 3 minutes) and enters it at checkout.
2. Store backend submits the code to TrustPay together with a webhook URL and a fresh per-payment webhook secret.
3. The customer confirms or rejects the payment in the TrustPay app.
4. TrustPay sends a signed webhook to the store, which forwards the result to the store frontend over WebSocket.

## 1. Store backend -> TrustPay backend

Endpoint:
- `POST /api/v1/payments/submit-code` (TrustPay backend, no authentication)

Request JSON fields (all required):
- `code` (string, 6 digits)
- `amount` (JSON number > 0, in PLN; stored rounded to 2 decimal places)
- `storeName` (your TrustPay username, exact match; if no account has this username the money goes to the TrustPay admin account)
- `webhookUrl` (public `http(s)` URL, e.g. `https://<store-host>/webhook/:correlationId`; localhost and private IPs are rejected)
- `webhookSecret` (random secret generated by the store for this payment, max 255 characters, no leading/trailing whitespace; TrustPay uses it to sign the webhook)

Response:
- `200 { "requestId": number }` - save it, the webhook for this payment carries the same `requestId`
- `400 { "message": string }` - validation error, invalid or expired code
- `429 { "message": string }` - too many failed attempts for this code (5 per minute)

This example generates `webhookSecret` with `crypto.randomBytes(32)` for every payment and keeps it in memory keyed by `correlationId`, so no shared secret has to be configured.

## 2. TrustPay backend -> Store webhook

**Important note:** If your website is running on localhost and is not exposed to a public URL, the webhook will not be delivered successfully because the TrustPay backend operates on a different network and cannot access your local environment.

Endpoint:
- `POST /webhook/:correlationId` (Store backend)

Sent once, after the payment reaches a final state:
- `CONFIRMED` - the customer confirmed; the money has already been transferred
- `REJECTED` - the customer rejected, or the 3-minute code window passed without a decision (sent within about a minute after expiry)
- `EXPIRED` - the customer discarded or regenerated the code in the app, or tried to confirm after it expired

Delivery:
- `POST` with `Content-Type: application/json`, sent only after the new state is committed in TrustPay
- a single attempt with a 10 s timeout and no retries; any `2xx` response counts as delivered, so respond quickly

Webhook body (JSON, field order not guaranteed):
- `requestId`: the id returned by `submit-code`
- `status`: `CONFIRMED` | `REJECTED` | `EXPIRED`
- `amount`: number with 2 decimal places
- `storeName`

Header:
- `X-Webhook-Signature`: lowercase hex HMAC-SHA256 of the raw request body, keyed with the `webhookSecret` sent for this payment; verify against the raw bytes, not a re-serialized JSON object

The store backend accepts the webhook only if:
- `correlationId` belongs to a payment it submitted that is still pending
- the signature matches (computed over the raw body bytes, compared in constant time)
- `requestId`, `amount` and `storeName` match the submitted payment

When a webhook is accepted, Store backend emits a WebSocket event to Store frontend:
- `type: "PAYMENT_FINALIZED"`
- `source: "webhook"`
- `correlationId`, `requestId`, `status`, `amount`, `storeName`, `receivedAt`

Pending payments are kept in memory, so a store backend restart drops them; use a database for this in production.
